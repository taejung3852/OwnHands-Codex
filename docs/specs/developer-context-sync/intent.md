## 1. 문제와 대상 사용자

AI가 개발을 진행하는 동안 사람이 목적·구조·변경 이유를 놓치면, 결과를 받아들일지 판단하거나 중단했던 작업을 재개하기 어렵다. 파일·커밋 목록만으로는 이러한 맥락이 충분히 연결되지 않는다.

또한 간단한 이해 요청에도 HTML 제작이 개입하는 기존 설명 경로는 사용자가 원하는 가벼운 맥락 복원과 맞지 않는다. 이는 사용자 경험에서 제기된 문제이며, 아직 처리 시간이나 토큰 비용으로 측정된 결과는 아니다.

대상 사용자는 **AI 코딩 에이전트와 함께 개발하면서 작업을 처음 이해하거나, 다시 합류하거나, 특정 설계·구현을 판단해야 하는 개발자**다.

## 2. 목표와 성공 기준

> 사람이 필요한 범위의 개발 맥락을 근거와 함께 이해하고, 현재 상태·변경 영향·남은 판단을 구분하여 다음 행동을 결정할 수 있게 한다.

| 목표 | 성공 기준 |
|---|---|
| **G1. 필요한 맥락을 복원한다.** | ONBOARD·CATCH-UP·DEEP-DIVE가 서로 다른 질문에 맞는 범위와 결과를 제공하고, 불필요한 전체 조사를 강제하지 않는다. |
| **G2. 설명을 근거와 연결한다.** | 중요한 설명의 출처를 추적할 수 있고, 설계 의도·구현·실행 결과·미확인을 혼동하지 않는다. 비교 기준 부재도 숨기지 않는다. |
| **G3. 사람의 판단 권한을 보존한다.** | 설명 후 원래 작업으로 돌아오며, 내용·저장·구현 관련 승인 상태를 자동으로 바꾸지 않는다. |
| **G4. Chat과 Codex에서 같은 역할을 제공한다.** | 두 환경에서 두 Skill을 제공하되, 관측 가능한 데이터 차이를 명시하고 공통 계약이 어긋나지 않게 한다. |

## 3. 범위와 제약

### 포함하는 범위

두 Skill의 역할·입출력·호출·복귀 계약, Chat과 Codex 제공, Chat `plan-design`의 설명 호출 연결, 기존 활성 설명 경로의 이전, 이를 확인할 수용 기준을 포함한다.

새 Skill 추가에 더해 활성 문서·호출·배포 경로의 정렬까지 후속 변경 범위에 포함한다.

### 유지하는 확정 조건

- **ELI5는 OwnHands 번들·필수 의존성에서 제외한다.** 사용자 global 파일은 건드리지 않는다.
- **`developer-context-sync`와 `human-diagram`을 Chat+Codex에 제공한다.** 두 배포물의 계약을 독립적으로 중복 관리하지 않는다. 기준 원본은 확정된 A안인 Plugin 경로로 두며, 구체적인 배포·동기화 계약은 연결 Spec을 따른다.
- **활성 `explain` 경로를 제거한다.** 과거 ADR·승인·실행 기록까지 삭제하거나 현재 상태로 고쳐 쓰지 않는다.
- **Intent 선택 호출 / Spec 승인 전 자동 1회는 Chat `plan-design`의 호출자 정책으로 유지한다.** Codex에는 이 자동 호출 정책이나 Chat의 Stage 승인 절차를 적용하지 않는다.
- **내용 승인과 저장 승인을 분리한다.** 설명 완료는 이해 확인·내용 승인·저장 승인·Build 승인을 대신하지 않는다.
- **자동 마이그레이션은 구현하지 않는다.** 신규 설치를 지원하고, 기존 설치는 사용자 파일을 보호하는 수동 이전 가이드로 처리한다.

### 책임 경계

Chat `plan-design`은 GORE 기반 기획·설계를 담당한다. Context Sync는 개발 맥락을 설명하고, Human Diagram은 필요한 구조·흐름을 근거 기반으로 표현한다. 설명 Skill에 요구사항 결정이나 설계를 위임하지 않는다.

Human Diagram은 특정 SDLC 단계나 Context Sync에 종속되지 않는 재사용 가능한 Companion이다. 독자가 어디부터 보고 어떤 방향으로 읽어야 하는지 알 수 있도록 하며, 세부 가독성 규칙과 검증 기준은 연결 Spec을 따른다.

## 4. 비목표

이번 작업에서 **Build·Test 재설계(#162), Review·Gate 정책 변경, 자동 수정·병합**은 다루지 않는다.

상시 watcher, 개인 이해도 프로파일링, 필수 퀴즈, 개인 checkpoint 영속화도 초기 구현에 넣지 않는다. HTML·이미지 렌더러나 새 MCP 서버를 도입하지 않으며, 설명 결과를 검증 성공의 증거로 사용하지 않는다.

## 5. Spec 연결

세부 입력 필드·실패 처리, 자동 1회 판정과 재검토 조건, 단일 원본·양쪽 배포 경로, 활성 자산 이전 범위, 수용 기준과 검증 방법은 [Spec v0.4](spec.md)에 연결한다.

Intent·Spec 내용 승인 및 저장 승인은 구현 실행, PR 생성 또는 Merge 승인을 포함하지 않는다.
